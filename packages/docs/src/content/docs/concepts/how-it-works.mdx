Magic Context manages two different kinds of context: it turns settled conversation into structured history, and it reclaims working material such as old tool output. You care about the distinction when the context percentage moves less—or more—than you expected.

## Follow one session

A new session starts with system instructions, relevant project memory, and an empty live conversation. Each turn appends user messages, agent messages, and tool results. Magic Context gives trackable content a `§N§` tag so the agent can later mark spent material with [`ctx_reduce`](/reference/tools/#ctx_reduce).

As the session grows, these regions reach the model in order:

![Prompt layout: system instructions first, then stable history blocks, then the growing live conversation and tagged tool outputs.](/diagrams/prompt-layout.svg)

- **System instructions** change only when their inputs, such as configuration or the active model, change.
- **History blocks** contain [compartments](/concepts/historian/) and injected [memory](/concepts/memory/). Materialized history stays byte-identical between cache rebuilds; new additions use a separate stable history block.
- **Live conversation** grows on every turn. Older settled messages can become compartments.
- **Tagged tool output** also grows. The agent can queue it for removal, and automatic reclaim can remove eligible old output during a pass that is already rebuilding the prompt cache.

The raw transcript remains in Magic Context's local database. A shorter prompt does not mean the stored session was deleted; the agent can retrieve omitted detail with `ctx_expand` or `ctx_search`.

## Separate historian from reduction

The historian and context reduction both make the active prompt smaller, but they act on different material and leave different results.

![Two parallel layers: the historian turns settled conversation into prompt-resident compartments, while reduction turns eligible tagged tool output into dropped placeholders.](/diagrams/two-layers.svg)

| Layer | Input | Result in the active prompt | When it helps |
|---|---|---|---|
| **Historian** | Settled user and agent conversation | Compartment summaries that **remain in the prompt** | Preserves the story, decisions, and outcomes of earlier work |
| **Reduction** | Tagged messages and tool outputs the agent no longer needs | Small dropped or truncated placeholders | Removes bulky working material after it has served its purpose |

### What shrinks what

| Source of prompt tokens | What can shrink it | What does not shrink it |
|---|---|---|
| Settled conversation | The historian replaces raw messages with compartments | `ctx_reduce` is not the normal way to build session history |
| Old tool output | `ctx_reduce`; automatic age-based reclaim on a cache-rebuilding pass; emergency reclaim | The historian does not summarize tool output into the history budget |
| Recent protected work | Nothing until it ages beyond the protected token window | Crossing the execute threshold does not override normal protection |
| Compartment history | Deterministic decay tiers during a later history rebuild | A historian run does not remove the history block |
| Injected memory text and optional memory mural | Their own budgets and selection rules | Neither the historian nor `ctx_reduce` treats them as live conversation |

A compartment starts detailed. As newer compartments accumulate and the history budget tightens, deterministic decay tiers render older or less important compartments with less detail. The oldest may disappear from the active prompt, while their source transcript remains retrievable. See [Historian](/concepts/historian/) for the complete lifecycle.

## Treat the execute threshold as a trigger

The execute threshold answers **when to run queued context work**, not **where the context percentage should land**. The default is 65% of the model's usable, output-reserved window. You can set a percentage per model or an absolute token threshold; see the [generated configuration reference](/reference/configuration/#context-management).

A normal pass works like this:

![Timeline: turns append while the cache prefix stays identical, crossing the threshold triggers one execute pass, queued and eligible automatic reclaim plus ready compartment history produce a new stable prompt at a variable size.](/diagrams/execute-pass.svg)

1. Turns append without rewriting the stable prefix.
2. Usage reaches the effective execute threshold. If a tool call is still waiting for its result, the normal pass waits for the next complete step boundary.
3. One execute pass applies due work together: queued `ctx_reduce` drops, heuristic cleanup, eligible age-based tool-output reclaim, and ready history updates.
4. The prompt becomes stable again at whatever size the retained material requires.

The landing point varies because the pass preserves several independent budgets and boundaries:

- the history budget;
- injected memory text and, when enabled, the memory mural;
- the recent protected token window;
- live work that has not settled yet;
- the mix of conversation versus tool output;
- how much tool output was queued or old enough to reclaim.

A session dominated by settled conversation can fall sharply when that conversation becomes compartments. A session dominated by recent or still-useful tool output may move only a little.

## Work through the numbers

These examples use the default 65% execute threshold and 15% history budget. They assume the stated context window is already the usable window after any output reservation. The compositions are illustrative—the budgets and trigger arithmetic are real, but Magic Context does not aim for the shown 45% landing point.

| Usable window | Execute trigger | History budget | Derived protected token floor |
|---:|---:|---:|---:|
| 200,000 | 130,000 | 19,500 | 16,000 |
| 1,000,000 | 650,000 | 97,500 | 50,000 |

### A 200k window

Suppose a pass begins at 140k tokens: 12k fixed prompt and memory, 12k existing history, 48k settled conversation, 28k recent work, and 40k tool output. The historian condenses the 48k settled span until total history fits 19k, while queued and eligible automatic reclaim removes 9k of tool output.

The next prompt is 90k tokens, or 45%: 12k fixed prompt and memory + 19k history + 28k recent work + 31k tool output. It landed at 45% because those inputs happened to total 90k—not because 45% is a target.

![Before-and-after bars for the 200k example: 140k before the pass and 90k after, with settled conversation replaced by history and some tool output reclaimed.](/diagrams/fold-before-after.svg)

### A 1M window

At the same defaults, the trigger is 650k, the history budget is 97.5k, and the derived protected floor is 50k. Imagine a pass beginning at 700k: 50k fixed prompt and memory, 70k existing history, 250k settled conversation, 130k recent work, and 200k tool output.

If the settled span becomes 25k of additional history and 25k of tool output is reclaimed, the next prompt is 450k, or 45%: 50k fixed + 95k history + 130k recent + 175k tool output. A different session could land much higher because a 1M window protects more recent token mass and allows a larger history block.

:::note[There is no target-size setting]
You can change when a pass triggers with the per-model threshold, improve agent-driven cleanup with `ctx_reduce`, choose a stronger historian model, and align cache assumptions with `cache_ttl`. None of these configures a post-pass percentage.
:::

## Understand the cost model

Providers can reuse a cached prompt prefix only while its bytes stay identical. Magic Context therefore keeps system instructions and materialized history frozen between folds. New conversation appends after that prefix, so ordinary turns reuse it byte for byte.

A fold or drop that changes earlier prompt content requires a cache rewrite. Magic Context treats that rewrite as a priced event: it batches historian updates, queued drops, and automatic reclaim into passes that are already rebuilding the prefix instead of paying for many small rewrites. Ten small folds can rewrite overlapping prompt bytes ten times; one larger fold rewrites them once.

`cache_ttl` tells Magic Context how long to assume the provider's cached prefix remains valid. Its default is `5m`, and it can vary by model. After that idle period, Magic Context may rebuild on the next turn because it assumes the old provider cache has expired. Setting `cache_ttl` does not change the provider's real cache lifetime or pricing; match it to the cache behavior of the route you use. See [Cache architecture](/concepts/cache-architecture/) for the internal layout and the [configuration reference](/reference/configuration/#context-management) for accepted forms.

## Compare compaction models

:::note[DCP-style compactor versus Magic Context]
| | DCP-style compactor | Magic Context |
|---|---|---|
| **Primary mental model** | Compact the active prompt toward a recurring working size | Preserve a cache-stable prefix, then batch structured history and reduction work |
| **Older conversation** | Replaced by a general compacted representation | Becomes typed compartments that remain in a budgeted history block and decay over time |
| **Tool output** | Often part of the same compaction decision | Managed separately through `ctx_reduce`, age-based reclaim on cache-rebuilding passes, and emergency recovery |
| **Expected graph shape** | May hover near a familiar level | Grows between passes, then lands wherever retained history, memory, recent work, and tool output total |
| **Summary quality** | Depends on the compactor model | Depends on the separately configured historian model |

Neither model is universally better. They optimize for different behavior. If you expect a session to hover near 100k, focus on the composition shown by `/ctx-status`, not just the total: compartment history is retained knowledge, while unreduced tool output is reclaimable working material.
:::

The context model is the same in OpenCode and Pi. The visible status and command delivery differ.
